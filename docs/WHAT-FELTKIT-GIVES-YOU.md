# What you write vs what FeltKit gives you

PersonalOS is a complete product: a personal assistant with chat, memory, tasks, reminders, files,
a daily briefing, a model that streams and proposes changes you approve, an audit log, and a Chrome
extension. This page shows how much of it is application code and how much is FeltKit.

The numbers below are generated from this repository by `feltkit measure` (`npm run measure`; this page's
section by `npm run measure:doc`) and checked in CI, so they can't drift from the code. Every file has one
class and the reason for it, listed in `measure.json`. Nothing here is estimated. Where a row says what you would otherwise
assemble, it lists components, not line counts.

## Capability by capability

| You get | How PersonalOS uses it | Without FeltKit you would assemble |
|---|---|---|
| **A database per environment**: FeltDB with schema enforcement, transactions, sequences and live change feeds. State lives in `.feltkit/<env>/state` locally, or a FeltDB server in production | Every record (conversations, memory, tasks, the action log) in `feltkit/app.ts`. An operation and its evidence commit together (`feltkit/_ops.ts`) | A database server, an ORM or query layer, migrations, and transaction handling around multi-record writes |
| **Accounts, sessions and roles**: password sign-up and sign-in, password reset, cookie sessions for the web, bearer sessions for other hosts, development users. Roles are checked on every interface | `auth: { accounts }`, three roles and three dev users in `feltkit/app.ts`. Sign-in screens in `src/auth.tsx`. Isolation between people is tested (`tests/assistant.test.ts`) | An auth library or service, a session store, CSRF protection, and a permission check in every endpoint and job |
| **An API from your functions**: every query, mutation and action is an authorized HTTP endpoint with a typed client (`api.*`). Functions with a `capability` are also published over AppPort and as MCP tools for agents | 45 functions. 13 published capabilities (`tasks.create`, `memory.add`, `briefing.today` …) that an agent can call over MCP with a session | An HTTP/RPC layer, input validation, client types kept in sync, and an MCP server with its own auth |
| **Live data in the browser**: `useQuery` re-runs when the data it read changes, from any client or process | Every screen. An approval made in a second session updates the first page without a reload (`e2e/acceptance.mjs`) | A WebSocket or SSE server, pub/sub between server processes, and client cache invalidation |
| **Background jobs and notifications**: jobs queued after commit and run as the person who queued them, re-authorized on each run. Notifications stored per person | Reminders, the daily check-in and the weekly review (`feltkit/reminders.ts`, `checkins.ts`, `weekly.ts`) | A queue and worker processes, a scheduler, retry and failure tracking, and notification storage |
| **Files**: uploads with size limits, short-lived download links, bytes stored in the same instance and owned by the person | Documents attached to projects (`feltkit/documents.ts`) | Object storage, signed URLs, metadata records and ownership checks |
| **Signed outbound webhooks**: delivery, signing, retries and history. An operator registers endpoints in Studio | `task.completed`, `reminder.fired` and `document.added` (`ctx.afterCommit.webhooks.emit`) | A webhook delivery system with signing, retries and a delivery log |
| **The model, without owning it**: `ctx.model.generate` streams to the UI. The environment chooses the model (Studio → Models, `feltkit model set`, or a Resolver reference) and the app never sees the key. It can be switched without a restart | The streamed chat turn (`feltkit/turn.ts`). Switching models A → B with no restart is verified against real models (`e2e/acceptance.mjs`) | An LLM SDK per provider, key storage, streaming plumbing to the browser, and model configuration and switching |
| **An agent that proposes, and people who approve**: model tool calls become proposals with durable records. The person approves in the app, the change runs once, as them, and the card shows a receipt | The app's capabilities are the model's tools. Reading tools run immediately; changing tools wait for approval in the chat (`feltkit/turn.ts`, `src/chat.tsx`, `useOwnActions`) | A tool-calling loop, an approval workflow, idempotent execution, and audit storage linking proposal, approval and result |
| **Streaming actions**: an `app.action` streams its events to the client over SSE, and the client can cancel it (Stop) | One action per chat turn (`useAction` in `src/chat.tsx`) | SSE endpoints, cancellation, and reconnect handling |
| **Sessions that end everywhere**: sign-out, revocation and expiry close open streams and clear the client's token on every channel | The web app and the extension. A revoked extension session is dropped within a second (`e2e/extension.mjs`) | Token revocation checks in every long-lived connection, and client cleanup |
| **Studio**: a development dashboard for data, models, webhooks, schedules, jobs and the agent | Printed by `npm run dev` | An admin panel |
| **Other hosts, same app**: the bearer client runs the same React app in a browser extension's side panel | `extension/`: connect, token storage, the panel host and a page bar (about 290 lines) | A second app or a separate API for the extension |
| **Build, start, deploy**: `feltkit build`, `feltkit start`, `feltkit deploy`, `feltkit readiness` | `npm run build`, `npm start`, `npm run deploy` | Build and server bootstrapping, health checks, and deployment scripts |

## What you still write

The product. In PersonalOS that is:

- **The app definition** (`feltkit/app.ts`): roles, which services are on, the model reference, and
  the collection schemas.
- **Domain operations** (`feltkit/`): what a task, a memory or a reminder is, and the rules for
  changing them. `_ops.ts` is the only code that changes state. Each operation reads its record back
  and writes an action-log row citing it.
- **The model turn** (`feltkit/turn.ts`): what the model sees and which tools it gets.
- **The UI** (`src/`): screens built on `useQuery`, `useMutation` and `useAction`, inside the shared
  stack-ui Shell.
- **Optionally, a built-in assistant without a model** (`assistant.ts`, `_interpret.ts`,
  `_dates.ts`): a hand-written parser for sentences and dates, so PersonalOS works with no model
  configured. An app that always uses a model can leave this out.

## What FeltKit does not do here

- **Semantic search.** Memory recall is keyword-based. FeltDB has no text or vector index yet.
- **Integrations.** Email, calendar and messaging are not connected. FeltKit's `app.integration`
  is the path; PersonalOS doesn't use it yet.
- **A model account.** Model features need a provider (an OpenAI-compatible endpoint, a gateway, or
  a Resolver reference). Without one, the built-in assistant answers.
- **Hosting.** You choose where it runs: `feltkit start` on a server, or a FeltDB server for state.
