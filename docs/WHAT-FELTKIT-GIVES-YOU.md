# What you write vs what FeltKit gives you

PersonalOS is a complete product: a personal assistant with chat, memory, tasks, reminders, files,
a daily briefing, a model that streams and proposes changes you approve, an audit log, and a Chrome
extension. This page shows how much of it is application code and how much is FeltKit.

The numbers below are generated from this repository by `npm run measure` and checked in CI, so they
can't drift from the code. Nothing here is estimated. Where a row says what you would otherwise
assemble, it lists components, not line counts.

The app defines 8 collections, 11 queries, 32 mutations and 2 streaming actions. FeltKit makes every function an authorized HTTP endpoint with a typed client, which the web app and the extension call. The 13 that declare a `capability` are also published over AppPort and as MCP tools for agents, with the same authorization. The app has 6 runtime dependencies: `@feltdb/feltkit`, `@stack-ui/core`, `@stack-ui/react`, `@stack-ui/tokens`, `react`, `react-dom`.

## Capability by capability

| You get | How PersonalOS uses it | Without FeltKit you would assemble |
|---|---|---|
| **A database per environment**: FeltDB with schema enforcement, transactions, sequences and live change feeds. State lives in `.feltkit/<env>/state` locally, or a FeltDB server in production | Every record (conversations, memory, tasks, the action log) in `feltkit/app.ts`. An operation and its evidence commit together (`feltkit/_ops.ts`) | A database server, an ORM or query layer, migrations, and transaction handling around multi-record writes |
| **Accounts, sessions and roles**: password sign-up and sign-in, password reset, cookie sessions for the web, bearer sessions for other hosts, development users. ## What you still write

The product. In PersonalOS that is:

- **The app definition** (`feltkit/app.ts`): roles, which services are on, the model reference, and
  the collection schemas.
- **Domain operations** (`feltkit/`): what a task, a memory or a reminder is, and the rules for
  changing them. `_ops.ts` is the only code that changes state. Each operation reads its record back
  and writes an action-log row citing it.
- **The model turn** (`feltkit/turn.ts`): what the model sees and which tools it gets.
- **The UI** (`src/`): screens built on `useQuery`, `useMutation` and `useAction`, inside the shared
  stack-ui Shell.
- **Optionally, a built-in assistant without a model** (`assistant.ts`, `_interpret.ts`,
  `_dates.ts`): a hand-written parser for sentences and dates, so PersonalOS works with no model
  configured. An app that always uses a model can leave this out.

## What FeltKit does not do here

- **Semantic search.** Memory recall is keyword-based. FeltDB has no text or vector index yet.
- **Integrations.** Email, calendar and messaging are not connected. FeltKit's `app.integration`
  is the path; PersonalOS doesn't use it yet.
- **A model account.** Model features need a provider (an OpenAI-compatible endpoint, a gateway, or
  a Resolver reference). Without one, the built-in assistant answers.
- **Hosting.** You choose where it runs: `feltkit start` on a server, or a FeltDB server for state.
